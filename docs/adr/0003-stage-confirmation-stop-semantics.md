# 阶段确认停止语义

交互式智能模式需要在“视图语义校正”和“零件语义重建”完成后让用户先审阅结果，再决定是否继续后续阶段。这个分支既不是系统失败，也不是用户在处理中途发起的即时取消；如果把三者混在一起，GUI 提示、批处理统计和后续恢复语义都会变得含糊。

## Considered Options

**A. 只有“继续”按钮，关闭窗口视为停止。**

界面最简，但“关闭窗口”语义不够明确，用户可能不知道这会结束整次处理。

**B. 把阶段停止并入现有“取消处理”。**

实现上可复用，但两者意图不同：取消是中断正在执行的任务，阶段停止是用户审阅完成后主动不放行下一阶段。

**C. 为阶段确认保留显式“停止 / 继续”分支，并把停止建模为独立状态。**

用户意图清晰，结果语义也能在 GUI、统计和日志中保持一致。选中。

## Decision

1. 阶段确认只属于交互式智能模式。
2. 阶段确认窗口使用“停止 / 继续”两个明确动作。
3. 用户在阶段确认点选择停止时，结果状态为 `stopped_by_user`。
4. `stopped_by_user` 不属于 `failed`，也不等同于 GUI 的“取消处理”。
5. 停止后，本次处理结束；之后若再次开始处理，系统发起新一轮任务，而不是恢复已停止任务。
6. 已完成阶段的结果仍可查看，但不构成可继续执行的会话。
7. 阶段确认窗口以人类可读汇报为主，可给出克制的建议动作提示；“继续”按钮文案保持简洁。
8. “停止”不再弹二次确认；按钮附近应说明停止后的结果。

## Consequences

- GUI 在 `stopped_by_user` 时显示“已停止”，不弹失败对话框。
- 批处理统计单独记录 `stopped_by_user`，不把它计入 `failed`。
- 追问继续维持独立语义：用户点“继续”后，如果下一步需要追问，再进入追问窗口。
- 如果未来需要“从停止点恢复”，应单独设计新的阶段恢复机制，而不是复用当前停止语义。
