# 阶段确认停止语义

交互式智能模式需要在“视图语义校正”和“零件语义重建”完成后让用户先审阅结果，再决定是否继续后续阶段。这个分支既不是系统失败，也不是用户在处理中途发起的即时取消；如果把三者混在一起，GUI 提示、批处理统计和后续恢复语义都会变得含糊。

## Considered Options

**A. 只有“继续”按钮，关闭窗口视为停止。**

界面最简，但“关闭窗口”语义不够明确，用户可能不知道这会结束整次处理。

**B. 把阶段停止并入现有“取消处理”。**

实现上可复用，但两者意图不同：取消是中断正在执行的任务，阶段停止是用户审阅完成后主动不放行下一阶段。

**C. 为阶段确认保留显式“停止 / 继续”分支，并把停止建模为独立状态。**

用户意图清晰，结果语义也能在 GUI、统计和日志中保持一致。选中。

## Decision

1. 阶段确认只属于交互式单图纸智能模式，不用于批处理。
2. 阶段确认只发生在“视图语义校正”和“零件语义重建”完成后；“建模指令生成”完成后不再追加确认。
3. 阶段确认窗口使用“停止 / 继续”两个明确动作。
4. 用户在阶段确认点选择停止时，结果状态为 `stopped_by_user`。
5. `stopped_by_user` 不属于 `failed`，也不等同于 GUI 的“取消处理”。
6. 停止后，本次处理结束；之后若再次开始处理，系统发起新一轮任务，而不是恢复已停止任务。
7. 已完成阶段的结果仍可查看，但不构成可继续执行的会话。
8. 新任务可以复用此前已缓存的分析结果，但不得复用此前的放行决定；命中缓存时仍需重新经过适用的阶段确认。
9. 追问窗口中的放弃补充信息不归入 `stopped_by_user`；它表示澄清未完成，而不是用户在阶段确认点主动停止后续阶段。
10. 当某阶段之后仍需追问时，系统先显示阶段汇报；只有用户选择“继续”后，才进入追问窗口。
11. 阶段确认窗口只聚焦刚完成的当前阶段，不在窗口内叠加此前阶段的汇报。
12. 阶段确认窗口以人类可读汇报为主；只有存在后续追问或明显风险时才显示克制的建议动作提示；“继续”按钮文案保持简洁。
13. 关闭阶段确认窗口等价于“停止”，因为系统没有获得继续放行的明确授权。
14. “逐阶段确认”作为保护性流程默认开启；当前不持久化用户上一次关闭该开关的选择。
15. 关闭“逐阶段确认”后，系统不再显示阶段汇报窗口，也不在这些停点等待确认，而是按原自动流程继续。
16. 阶段确认日志应记录阶段名、用户动作（继续 / 停止）以及当前汇报是否来自缓存结果。
17. 当“逐阶段确认”开启时，两个既定阶段一律等待用户显式确认；置信度高低只影响汇报提示，不决定是否跳过确认。
18. “停止”不再弹二次确认；按钮附近应说明停止后的结果。

## Consequences

- GUI 在 `stopped_by_user` 时显示“已停止”，不弹失败对话框。
- 批处理统计单独记录 `stopped_by_user`，不把它计入 `failed`。
- 分析缓存可以减少重复计算，但不会把用户上一次的“继续”决定隐式带入下一次任务。
- 追问继续维持独立语义：用户点“继续”后，如果下一步需要追问，再进入追问窗口。
- 若未来需要批量人工审核，应另行设计批量审阅机制，而不是把当前阶段确认语义直接搬入批处理。
- 如果未来需要“从停止点恢复”，应单独设计新的阶段恢复机制，而不是复用当前停止语义。
