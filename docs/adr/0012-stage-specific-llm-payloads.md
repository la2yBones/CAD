# 阶段化 LLM 输入载荷

智能处理管线不再把全量原始实体无差别传给各个大模型调用阶段。全量 `geometry_data.entities` 只供本地分析层使用；大模型调用应按职责接收阶段化结构化输入：视图语义校正使用视图判定载荷，语义生成使用语义理解载荷，建模指令生成使用建模任务载荷。

## Decision

1. LLM 输入载荷必须按调用阶段设计，不继续复用“把解析结果、上下文和 schema 全部塞进 prompt”的通用形态。
2. 视图语义校正阶段接收视图判定载荷，只包含布局摘要、候选视图、投影关系证据、实体类型统计、轻量尺寸摘要和作为弱证据的文件名提示；不包含视频策略、完整 JSON Schema、全量原始实体、实体样本、完整视图实体列表或建模脚本约束。该阶段默认关闭 thinking/reasoning，优先低成本、低噪声、稳定 JSON 输出。
3. 语义生成阶段接收语义理解载荷，用关键轮廓、轴线、圆/弧/孔、尺寸绑定候选、投影关系和不确定项等证据摘要生成 `part_semantics`；不包含全量原始实体、完整视图实体列表或大量 entity pair 明细。
4. 建模指令生成阶段接收建模任务载荷，由 `object`、`features`、`dimensions`、`constraints` 和 `recovery_hints` 组成；不直接接收原始几何实体、完整 `part_semantics`、视图实体列表、本地关系明细或本地展开的操作步骤。
5. 建模任务构建器只是合同转换器，负责结构化裁剪和任务装配；它不重新理解图纸、不按具体零件类型写特殊规则，也不从缺失字段中推断新语义。
6. 如果阶段化载荷无法表达关键判断，应增强本地证据摘要或进入追问/部分完成流程，而不是把全量实体重新塞回 LLM 作为兜底。

## Considered Options

**A. 继续向 LLM 传递宽上下文。**

这种方式实现最简单，但会导致 prompt 过大、硬截断、阶段职责混杂和无关字段污染。例如视图语义校正中出现视频策略，建模指令生成阶段重新看到大量几何实体，会让模型重复理解图纸而不是专注当前阶段任务。

**B. 所有阶段都极简化，只传最终语义。**

这种方式 token 成本最低，但会伤害语义生成质量。第二阶段仍承担“看懂零件”的职责，必须保留关键几何证据摘要，不能压缩成第三阶段那种施工单。

**C. 本地保留全量实体，LLM 只接收阶段化载荷。**

本地解析、视图初判、尺寸提取、关系分析继续使用全量实体；LLM 只接收各阶段需要的结构化证据或任务。选中。

## Consequences

- 需要为三个 LLM 调用阶段分别维护载荷构建逻辑，而不是在调用点随手拼 prompt。
- 第一阶段应移除视频策略、完整 schema、字符串硬截断和实体样本，并默认关闭 thinking/reasoning。
- 第二阶段需要设计足够强的关键几何证据摘要，避免因过度压缩损失零件理解质量。
- 第三阶段会更像脚本生成器：它根据建模任务载荷生成 FreeCAD 脚本，不再重新读取图纸底层实体。
- 后续测试应锁定边界：各阶段 prompt 不应包含被禁止的全量实体、视图实体列表、无关多模态字段或完整旧上下文。

## Implementation Notes

- 视图语义校正阶段由 `view_decision_payload.py` 构建视图判定载荷，`LLMViewAnalyzer` 只序列化该载荷。
- 语义生成阶段由 `SemanticUnderstandingPayloadBuilder` 构建语义理解载荷，保留视图结构、关键几何证据摘要、尺寸裁决和语义策略；不直接传递 `source_entities`、视图实体列表或局部关系明细。
- 建模指令生成阶段由 `ModelingTaskBuilder` 构建建模任务载荷，`SemanticReconstructionPipeline` 将该载荷传给 `FreeCADInstructionGenerator`。
- `FreeCADInstructionGenerator` 的 prompt 只包含建模任务载荷；保留旧参数用于兼容调用和失败降级，但这些宽上下文不再直接进入第三阶段 LLM 输入。
- 三个 LLM 阶段均已有边界测试，防止被禁止的宽上下文字段重新进入 prompt。
