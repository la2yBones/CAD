# ADR 0016: 最小人工介入与阶段内模型自纠

## 状态

Accepted

## 背景

系统此前在语义不足或建模不确定时，会较早进入用户澄清流程。实际使用中，澄清问题经常表现为开放式文本输入，例如要求用户判断某个尺寸是否为高度、厚度或局部特征尺寸。对复杂工程图而言，这类问题对用户并不友好，也容易把本应由系统完成的图纸理解责任转移给用户。

同时，系统已经具备阶段化大模型调用、本地校验、尺寸权限池、建模任务载荷、脚本可执行性校验和逐阶段确认等机制。相比频繁要求用户补充语义，更合理的方向是让系统在每个阶段内部优先通过大模型自纠和本地校验消化问题，并把过程透明展示给用户。

## 决策

系统采用最小人工介入原则。

用户不再作为常规语义补全者。智能处理应优先通过阶段内模型自纠、本地校验、风险记录和阶段报告继续推进。逐阶段确认主要作为进度汇报和监督点，用于让用户查看阶段结论、证据、风险、自纠记录和下一步动作，并允许用户选择继续、终止、重试或触发自纠。

系统新增阶段内自纠会话作为领域角色。它负责在单个 LLM 调用阶段内组织模型自纠回合，接收本地校验问题、阶段证据包、候选解释和输出合同，控制自纠轮次，构造给大模型的修正请求，并输出修正后的阶段结果、用户候选确认或失败报告。

每个阶段最多执行 2 轮模型自纠。达到上限后不得继续后台重试，必须转为可见出口：带风险继续、用户候选确认、待恢复任务或明确失败报告。

工程语义分歧默认不直接阻塞用户。系统应先让模型给出解释、依据、风险和推荐判断，并在阶段报告中记录后继续推进。只有影响主体外形、主要体量、关键尺寸来源或建模路径安全边界，且模型自纠后仍无法形成可审计判断时，才进入用户候选确认或待恢复任务。

用户候选确认不是常规流程中的必经人工补全步骤。它只在系统越过安全边界仍无法闭合，或用户在阶段确认中指出阶段结果错误时出现。候选确认界面应展示可选解释、推荐项、依据和风险，并保留可选补充说明输入框。

## 实施边界

阶段内自纠会话应作为管线层领域能力，而不是 GUI 能力或单个校验器能力。

校验器只负责输出结构化问题，例如问题代码、严重级别、用户可见描述、可修正性、影响范围和建议修正目标。校验器不直接调用大模型，也不决定是否继续。

阶段生成器只负责根据阶段载荷和自纠请求生成或重生阶段结果。它不维护自纠轮次，不直接处理 GUI 操作。

GUI 只负责展示阶段状态、自纠状态、候选项、风险和监督动作。GUI 不直接拼接给大模型的修正 prompt，也不解释图纸语义。

阶段内自纠会话的输入合同应包含：

- `stage`：所属阶段，例如视图语义校正、图纸语义裁决、零件语义重建或建模指令生成。
- `round_index` 和 `max_rounds`：当前轮次和最大轮次。
- `stage_payload`：该阶段原始结构化输入载荷。
- `previous_output`：上一轮模型输出或阶段结果摘要。
- `validation_issues`：本地校验问题列表。
- `output_contract`：本阶段必须满足的输出合同。
- `evidence_refs`：可追溯证据 ID 或证据摘要，不重新传输全量原始实体。

阶段内自纠会话的输出合同应包含：

- `status`：`corrected`、`continue_with_risk`、`needs_user_confirmation`、`pending_recovery` 或 `failed`。
- `corrected_output`：修正后的阶段输出。
- `self_correction_log`：触发原因、轮次、问题、修正目标和结果。
- `risk_notes`：允许继续时必须展示的风险说明。
- `candidate_options`：需要用户候选确认时的选项、推荐项、依据和风险。
- `next_action`：继续、终止、重试、自纠、进入待恢复或生成部分结果。

阶段确认应逐步从布尔放行扩展为监督动作。最小动作集合为：

- `continue`：接受当前阶段报告并继续。
- `stop`：终止当前图纸处理。
- `retry_stage`：重跑当前阶段。
- `self_correct`：要求当前阶段进入模型自纠。

## 适用阶段

阶段内自纠优先覆盖四个大模型调用阶段：

- 视图语义校正：处理视图数量、视图角色、投影关系和输出合同问题。
- 图纸语义裁决：处理尺寸权限、候选解释、证据引用和裁决合同问题。
- 零件语义重建：处理零件类型、特征列表、关键尺寸、风险文本和结构化 schema 问题。
- 建模指令生成：处理 FreeCAD 脚本合同、建模约束和可执行性校验问题。

不同阶段可以使用同一个阶段内自纠会话抽象，但每个阶段必须提供自己的输出合同、校验问题和修正请求装配器。

## 后果

- 用户交互从“回答系统不清楚的问题”转为“监督系统判断是否合理”。
- 复杂图纸处理时，系统会优先自纠并继续推进，减少模糊澄清弹窗。
- 模型自纠必须有用户可见状态，不能作为后台静默重试隐藏起来。
- 阶段报告需要记录自纠触发原因、轮次、校验问题、修正目标、本轮结果、风险和下一步动作。
- GUI 逐阶段确认需要从简单继续/停止，扩展为继续、终止、重试和触发自纠等监督动作。
- 校验器只产出问题，GUI 只展示状态和候选项，阶段生成器只负责生成或重生阶段结果，自纠会话负责组织模型修正流程。
